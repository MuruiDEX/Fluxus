## Where things live

| Concern | Location |
|---|---|
| UI routes, layouts | `frontend/app/` |
| Reusable UI (shell, cards, badges, dialogs, engine controls) | `frontend/components/system/` |
| Domain model | `frontend/lib/domain/types.ts` |
| Client state | `frontend/lib/store/app.ts` (Zustand, one store per slice) |
| Business logic / simulated AI | `frontend/lib/sim/` — pure core (`core.ts`), loop manager (`engine.ts`), Team Lead questioning (`teamLead.ts`) |
| Demo data | `frontend/lib/data/seed-northstar.ts` (scoped by `businessId`) |
| Unit tests | `frontend/lib/**/*.test.ts` (Vitest) |
| Browser E2E | `frontend/e2e/` + `frontend/playwright.config.ts` |
| Styles / design tokens | `frontend/app/globals.css` (Tailwind v4 `@theme`) |
| Build/lint/test configs | `frontend/` (each tool resolves relative to its own config file) |
| API / DB / server | **does not exist** — reserved: `backend/README.md` |

## Frontend ↔ backend interaction

There is none at runtime. The frontend is self-contained:

1. `lib/sim/engine.ts` owns the single execution loop (start/pause/resume/stop/reset).
2. Each tick runs pure `stepScope()` (`lib/sim/core.ts`) and writes results into Zustand stores.
3. UI components subscribe to stores only — no component owns timers or mutates tasks directly.
4. Approval decisions flow `approvals store → applyApprovalToExecution → gated task resumes/revises`.

The `backend/` contract (when approved) is specified in `backend/README.md`:
mirror `lib/domain/types.ts` and match `stepScope` semantics tick-for-tick.

## Where to put new code

- New screen → `frontend/app/(app)/<name>/page.tsx` (+ reuse `components/system/` primitives; do not invent a second design language).
- New shared UI → `frontend/components/system/`.
- New state slice → extend `frontend/lib/store/app.ts` (bulk `replace*` setters are engine-only).
- New execution behavior → pure functions in `frontend/lib/sim/core.ts` + Vitest coverage; loop/scheduling only in `engine.ts`.
- New demo content → `frontend/lib/data/seed-northstar.ts`, always tagged `businessId`, never as product logic.
- New unit test → next to the module (`*.test.ts`); new journey → `frontend/e2e/`.
- New server anything → `backend/` per its README, only after explicit approval.

## What stays in the root, and why

- `package.json` — root orchestration scripts delegating with `npm --prefix frontend`
  (no dependencies of its own; avoids forcing directory changes per operation).
- `.gitignore` — repo-wide ignores (covers `frontend/` build/test output).
- `README.md`, `docs/` — entry point + contributor documentation.
- `frontend/`, `backend/` — the two product areas.

Everything else (sources, configs, lockfile, `node_modules`) belongs to exactly
one area: `frontend/`. Nothing is duplicated between root and `frontend/`.
